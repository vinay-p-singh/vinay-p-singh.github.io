Part one · The thesis

The comforting message

Software fundamentals matter now more than they actually ever have. Matt Pocock

The fear: AI writes the code, so twenty years of engineering craft is now worth nothing.

The argument: the opposite. AI raises the value of a good codebase and raises the cost of a bad one — because a codebase you cannot safely change is a codebase AI cannot safely accelerate.

The chain

  • AI in a good codebase performs really well
  • So good codebases matter more than ever
  • So software fundamentals matter more than ever

Part one · The failure that started it

The spec-to-code loop degrades

Write a spec, generate code, don't look at the code. Bug? Change the spec, run the "compiler" again.

What actually happens: run one gives code, run two gives worse code, run three gives worse still. Keep going and you have garbage.

This has a name already — software entropy. Every change made while thinking only about that change, and never about the design of the whole system, degrades the system.

Complexity (Ousterhout)

Anything about the structure of a system that makes it hard to understand and modify. A bad codebase is one you cannot change without causing bugs.

The slogan being sold

"Code is cheap." Ignore the code, let it manage itself.

That is vibe coding by another name.

software entropythe tendency of a codebase to drift into disorder as changes pile up, unless someone pushes back complexitynot difficult maths, but anything about a system's structure that makes it hard to understand or change spec-to-coderegenerating the whole codebase from a written specification instead of editing the code vibe codinggenerating code from prompts and shipping it without reading what came out
A Philosophy of Software Design — John Ousterhout · The Pragmatic Programmer — Hunt & Thomas

Part one · Failure mode 1

"The AI didn't build what I wanted"

Diagnosis. No one knows exactly what they want. Talking to the AI is requirements gathering — and you and it do not share the same picture.

The design concept (Frederick Brooks): when two parties design something together, the idea of the thing floats between them. It is not an artifact. You cannot put it in a markdown file. It is the invisible theory of what is being built.

Fix. Reach a shared design concept before producing any plan asset.

The skill, in two lines 
Interview me relentlessly about every
aspect of this plan until we reach a
shared understanding.

Walk down each branch of the design
tree, resolving dependencies between
decisions one by one.

Reported in the talk: 40, 60, sometimes 100 questions before it is satisfied. The conversation then becomes the PRD or the issue — not the other way round.

Contrast with default plan mode: it is eager to produce an asset and start working. Alignment first is cheaper than rework.

design conceptthe shared mental picture of what is being built; it lives between people, not in a file design treethe branching set of decisions a design implies, where each choice opens or closes later ones requirements gatheringworking out what someone actually needs, as opposed to what they first asked for PRDproduct requirements document — the written statement of what will be built, and why

Part one · Failure mode 2

"The AI is way too verbose"

Diagnosis. You are talking across purposes. This is exactly the old developer-and-domain-expert gap: they use terms you don't hold, you translate them into code neither of you can verify.

Fix — a ubiquitous language (DDD): conversations among developers, expressions in the code, and conversations with domain experts all derive from the same domain model.

In practice, a markdown file of agreed terms — scanned from the codebase, then kept open while planning.

Reported in the talk
  • Planning quality goes up
  • The model's own thinking traces get shorter — it stops narrating around a concept it now has a word for
  • Implementation lands closer to what was planned
ubiquitous languageone agreed word per concept, used identically in conversation, documents and code domainthe subject the software serves — claims, payments, usage metrics — not the software itself domain expertthe person who knows that subject deeply but does not write the code thinking tracesthe model's visible internal reasoning before it produces an answer
Domain-Driven Design — Eric Evans

Part one · Failure mode 3

"It built the right thing, and it doesn't work"

Obvious layer: feedback loops. Static types. Browser access for front-end work. Automated tests.

The non-obvious part: even with those loops, the model does not use them the way a veteran does. It writes an enormous amount, then thinks "I should probably type-check that."

Outrunning your headlights. The rate of feedback is your speed limit.
Why TDD, specifically

Not because tests are virtuous. Because TDD is a mechanical constraint that forces small steps:

  • Write the test first
  • Make it pass with the smallest change
  • Refactor — and consider the design

The model cannot outrun a loop it has to close on every step.

feedback loopanything that tells you quickly whether the last change was right — types, tests, a browser static typeschecks that catch mismatched data before the code is ever run outrunning your headlightsmoving faster than you can see, so a mistake surfaces long after it was made TDDtest-driven development — failing test first, smallest change to pass it, then improve the design

Part one · Failure mode 4

Testing is hard — because the decisions are entangled

Every test forces coupled choices:

  • How big is the unit under test?
  • What gets mocked?
  • Which behaviours are even worth asserting?

Test a whole application and it is flaky, so you test fewer behaviours. Test this unit and you must mock that one. None of these decisions is independent.

The pivot back to code

Good codebases are testable codebases.

Which closes the loop: better structure → better feedback loops → better feedback to the model → better code out.

Testability is an architectural property, not a testing-discipline property.

unitthe slice of code one test exercises; choosing its size is the first hard decision mocka stand-in for a real dependency so a test can run without it flakya test that passes and fails on identical code, so it stops meaning anything testabilityhow easily a system can be verified from outside — a property of its design, not its tests

Part one · The central structural idea

Deep modules, not shallow ones

Shallow — what gets generated by default

6 interfaces to learn · 18 units of functionality

Deep — the same code, bounded

2 interfaces to learn · 18 units of functionality

Same functionality on both sides. The only difference is where the boundaries fall — and how much blue line you have to learn to use it. A module is deep when the implementation is significantly more complex than its interface, and shallow when the interface is nearly as complex as what sits behind it. Bertrand Meyer put it as an iceberg: a small tip above the water, a large body beneath.

Who owns what

You design the interfaces carefully. The implementation inside can be delegated.

Why it is testable

The boundary is simple: test at the interface, verify through the interface, done. A codebase that rewards TDD.

Why the model does better

Fewer, clearer things to navigate before it can change anything correctly.

modulea self-contained piece of the system with a boundary drawn around it interfacethe small surface a module exposes — everything a caller has to know about it deep modulea lot of functionality hidden behind a small, simple interface shallow modulelittle functionality behind a comparatively large or fiddly interface

Part one · The canonical example

Five functions, fifty years

Deep — the Unix file interface

int     open (const char* path, int flags, mode_t permissions);
ssize_t read (int fd, void* buffer, size_t count);
ssize_t write(int fd, const void* buffer, size_t count);
off_t   lseek(int fd, off_t offset, int referencePosition);
int     close(int fd);

Everything a caller must learn to use a filesystem. Behind it: disk devices, on-disk data structures, permissions, concurrent access, caching, crash recovery.

Shallow — a real one, from the book

void addNullValueForAttribute(String attribute) {
    data.put(attribute, null);
}

The interface is longer than the implementation. The caller learns a new name, a new place to look, and a new thing that can drift — and receives one line they could have written themselves.

This is what gets generated at volume when nobody is deciding where the boundaries go.

The part that matters for AI

Unix filesystem implementations have been rewritten many times over. Those five signatures have not changed.

Every one of those rewrites was invisible to callers — because the interface held still. That is the property you are buying. An implementation you can hand to a model and have replaced wholesale, without anything upstream needing to know, is exactly a deep module. Without that boundary, "let the AI rewrite it" means "let the AI rewrite everything that touches it".

signaturethe name, parameters and return type of a function — the part callers depend on file descriptorthe small integer Unix hands back to stand in for an open file information hidingkeeping design decisions inside a module so nothing outside can depend on them
Both examples from John Ousterhout, A Philosophy of Software Design, ch. 4 — “Modules Should Be Deep”.

Part one · Failure mode 5

"I can ship more than ever, and my brain can't keep up"

More output means more review, more context, more system held in your head at once. A shallow codebase forces you to hold all of it too — not just the model.

Deep modules give you gray boxes. Design the interface. Understand the purpose. Verify from the outside. Don't read every line inside.

The boundary of that permission is risk — finance, security, safety, anything correctness-critical still gets read. Most modules in most apps do not.

Tip five

Design the interface.
Delegate the implementation.

The consequence for planning

If modules are the unit of delegation, then every plan has to name the modules and interfaces it touches — not just the feature it adds. Module structure becomes part of the ubiquitous language.

gray boxsomething judged by its boundary and behaviour without reading the inside — between a black box (opaque) and a white box (fully inspected) correctness-criticalcode where being wrong is expensive: money, safety, security, compliance

Part one · The close

Invest in the design of the system every day

Spec-to-code does not invest in the design of the system.
It divests from it.

Every regeneration that ignores structure spends the system's remaining changeability.

The division of labour

AI is an excellent tactical programmer — the sergeant on the ground making the change.

Someone has to be operating at the strategic level: architecture, requirements, risk, what "correct" means. That is you, and it needs exactly the fundamentals we have used for twenty years.

Part two

What to actually do

Five failure modes, six practices. What each one is for, what it costs, and what the evidence actually supports.

The through-line

A rule that cannot fail is not a rule.

Prose, comments and good intentions share one property: nothing happens when they stop being true. Most of what follows is about moving rules somewhere they can go red.

Why it bites harder now

None of these practices are new. What changed is the volume of code arriving against them. A weak boundary that used to erode over a year now erodes over an afternoon.

The standard used here

Each claim is a published result, a canonical source, or a mechanism you can run yourself and watch fail. Anything invented to make a shape visible is marked ILLUSTRATIVE — so nothing here has to be taken on trust in someone else's codebase.

invarianta rule that must stay true no matter what the data does ubiquitous languageone agreed word per concept, used in code, docs and conversation alike go redfail a test — the moment a machine notices something stopped being true

Part two · Ubiquitous language

Name things once, and write it down

Eric Evans named this in Domain-Driven Design: one agreed word per concept, used identically in conversation, documentation and code. It reads like bookkeeping. It is the cheapest defect prevention available.

The failure it prevents

Two people use one word for two different things and never find out. The API author means one thing by customer; the billing team means another; the person writing the code splits the difference and produces something that is nobody's definition.

Nothing surfaces the collision, because both sides keep using the word and both sides keep being understood — right up until a number is wrong and no one can say whose meaning was the correct one.

This gets sharply worse with generated code. A model reads your words to decide what your system means; one word carrying two meanings produces two behaviours, and it will pick whichever the surrounding text implied.

What the document actually holds

EntryWhy it earns its place
The agreed termOne word per concept — not two, and not a synonym per team
The central entityThe one thing everything else hangs off, so every conversation starts in the same place
Pairs that get conflatedTwo words a newcomer will treat as interchangeable, and the distinction that actually matters
Words the code and the interface disagree onThe equivalence written down as a decision, rather than tolerated silently
Terms deliberately retiredThe word that came to mean three things, and what replaced it

ILLUSTRATIVE In the ordering system used from here on: order is the central entity; captured and settled are the pair everyone conflates; the API says customer where the interface says account.

The fourth row is the one everyone skips. A disagreement you record stops costing you. A disagreement you tolerate silently gets rediscovered by every person and every model that arrives after you.

Part two · Making rules fail-able

The invariant register

A numbered list of the rules the system must never break, kept in one place. Each entry names the test that enforces it — or is explicitly marked as unenforced. Nothing else is allowed in the list.

What a rule looks like once it has teeth

ILLUSTRATIVE The same ordering system. Your rules will be your own; the three columns are the part to copy.

#InvariantEnforced by
INV-1An order total equals the sum of its line items, after discount and taxtest_order_totals
INV-2A refund never exceeds the amount originally captured for that ordertest_refunds
INV-3A cancelled order contributes zero to every revenue figuretest_revenue
INV-4An order is never attributed to a customer the source system did not nameNOT ENFORCED

The number is only a handle, assigned in the order rules were found — it is not a priority. It earns its keep the first time someone writes INV-2 in a review, a commit message or a prompt instead of re-explaining the rule from scratch.

The principle

A rule that lives only in a comment cannot be violated. It can only be contradicted — silently.

The register is the ubiquitous language with teeth: the shared vocabulary plus the mechanism that makes disagreement fail loudly.

Two categories, never three. A rule is either enforced by a named test, or explicitly marked as unenforced. There is deliberately no third bucket for “we mean this, but nothing checks it” — that bucket is precisely where wrong beliefs go to live undisturbed.

Part two · Test-first

A test written after the code encodes the code

The common loop is: build the feature, then wrap tests around what was built. Those tests pass. They also encode whatever the code already does, including its mistakes.

The failure it produces

A wrong behaviour acquires a passing test. The mistake is no longer merely present — it is defended. Correcting it now looks like breaking something, and CI will agree with the mistake.

A test written first would have been unpassable against that behaviour. That is the whole difference: a test-first test can tell you your belief about the system is false. A test-last test structurally cannot.

What the evidence reports

Four industrial teams — three at Microsoft, one at IBM — recorded 40–90% lower pre-release defect density after adopting TDD, measured against comparable projects that did not. The same study is candid about the cost: initial development took longer.

Nagappan, Maximilien, Bhat & Williams, Empirical Software Engineering, 2008.

What the test-last loop produces 
write code
observe behaviour
assert the behaviour you observed   ← green, and meaningless
What the test-first loop produces 
assert the behaviour you want
watch it fail — for the predicted reason
smallest change that makes it pass
run everything; a failure elsewhere means
the change is wrong, not the test

The last line is the one that gets dropped under pressure, and it is the one that matters: a failure somewhere else means your change is wrong, not that the other test is inconvenient.

test-lastwriting the test after the code, so it records what the code does rather than what it should do pinned by a testa wrong behaviour protected by a passing test, so correcting it looks like breaking something green / reda suite where every test passes / one where something fails

Part two · The three practices, joined

One rule, all the way through

Naming, registering and testing are not three habits. They are one move in three steps. Here is a single rule making the whole journey. ILLUSTRATIVE

01 · It starts as a sentence 
README.md
Refunds are capped at the
original charge.

True the day it was written. Since copied into the API docs, a comment and a ticket. Nothing anywhere fails if the code stops honouring it.

02 · It becomes a numbered rule

The sentence moves into the register as INV-2, marked NOT ENFORCED.

Nothing is safer yet. But the gap now has a name, a number, and a place someone will actually look — instead of being invisible by default.

03 · The test comes before the fix 
assert an over-refund is rejected
run it → red, because it isn't
cap the refund at captured
run it → green

The red step is the proof. Green on the first run would have meant the belief was already true and this rule was never the risk.

04 · The register closes the loop

INV-2 now reads test_refunds where it said NOT ENFORCED.

The README sentence can stay or go — it no longer matters which, because it is no longer the thing holding the rule up.

What the journey actually changed

The rule was true at step 01 and true at step 04. Nothing about the system's behaviour is different because it was written down. What changed is what happens when it stops being true — at step 01, nothing; at step 04, a red build with a number attached to it. That is the entire value of all three practices, and it is why prose was never a weaker version of a test. It is a different kind of thing.

reda failing test — here, the evidence that the rule was genuinely unguarded cappedlimited to a maximum; the behaviour INV-2 requires

Part two · Deep modules in practice

How to split something safely

Knowing that modules should be deep does not tell you how to get there from a file that has quietly become the entire system.

01 · Freeze the output first

Before touching structure, capture a golden master — a full snapshot of the output plus a hash of it. Then prove the check is sharp enough to catch a one-character change. An unverified safety net is not a safety net; it is the feeling of one.

02 · Cut at boundaries you can name

Not “split this 2,000-line file into four”. Say what each piece is for first. If the responsibility does not fit in one sentence, the boundary is in the wrong place — and what you get back is the left-hand picture below.

03 · Prove the parts rejoin

Assert that the reassembled output is byte-identical to the golden master before deleting the original. Not equivalent. Not equivalent-looking. Identical.

04 · Do not move the test seam

Leave the place where a test substitutes a fake exactly where it was. Relocating the seam during a restructure gives you two changes at once and no way to tell which one broke it.

Deep, not merely split
Split — 3 interfaces
Deep — 1 interface

Both sides hold the same six units of functionality — the difference is how much blue line a caller has to learn. Breaking a large file into many small ones lands you on the left: same behaviour, more interfaces, nothing hidden. In a well-split system the largest module is often large on purpose, because it is the one concealing the most.

golden mastera saved copy of known-correct output; the test fails if new output differs at all byte-identicalliterally the same file, not merely equivalent-looking test seamthe one place a test can point the code at a fake instead of the real thing

Part two · Entropy control

Making decay fail a test instead of a user

Systems rarely break outright. They drift — a copy falls behind, a rename lands in one place and not another, a literal acquires a fifth home. None of it announces itself. It surfaces much later as a wrong answer nobody can account for.

The general fix

For every kind of drift you can name, write the test that goes red when it happens. A forgotten sync then costs you a failed build instead of someone's wrong number weeks later.

Pair it with an instructions file scoped to exactly the files that trigger the rule — so the rule reaches whoever edits them, human or agent, at the moment they edit them.

Two guards worth writing on day one

One home for every magic value

Assert that a literal appears in exactly one module. The first run is the informative one, and you can have it in ten minutes: the number of copies you believe exist is not the number the grep finds.

Delete the fallback and let it raise

Before keeping a defensive default, measure how often it actually fires against real data. A fallback that has never once fired is not protection — it is a silent branch waiting to substitute something plausible for something true. Delete it and make the failure loud.

magic stringa bare literal value repeated across the code, with no name and no single home fallbacka default used when the expected value is missing — convenient, and very good at hiding real problems raisestop and report the error instead of quietly substituting something plausible guard testa test whose only job is to stop a known bad habit reappearing

Part two · What generalises

Lessons that only arrive from practice

MECHANISM Not studies. Each of these is something you can reproduce on your own code in an afternoon and watch fail.

01

Red for the wrong reason is not red

A test can fail with exactly the message you expected, for a completely different cause — a fixture writing to a key nothing reads, say. Read the failure before writing the fix.

02

Fixtures must be faithful, not convenient

Invented data puts the awkward cases in isolation, where they are easy to handle. Real data puts them beside everything else. A test that only ever sees the tidy arrangement is passing for reasons that will not survive contact with production.

03

Never derive state from the output you are about to overwrite

Read filter state back from the rendered page and the filter lags by one render — the value you read is the one you are in the middle of replacing. State lives in the state object; the page is an output, not a store.

04

Pass now as an argument

Anything time-dependent should take the current time as a parameter instead of reading the clock. Month-end and leap-year arithmetic become deterministic and testable the moment it does. The same argument applies to randomness, environment and the filesystem.

05

Correct is not the same as legible

A control can work perfectly and still be reported as a bug, if every surface it changes is somewhere the user is not looking. Give feedback at the point of interaction, not only where the effect lands.

renderone pass of redrawing the page from the current state fixturethe prepared data a test runs against deterministicthe same inputs always give the same result — which is what makes it testable

Part two · Honest accounting

What it costs, what it buys

The cost

  • More files to navigate, not fewer — modules multiply even as complexity per module falls
  • A suite that has to stay green on every change, and has to be maintained like code
  • A domain document and an invariant register that must be updated with the code — otherwise they become the prose problem they were written to solve
  • Longer initial development time; the research is explicit about this

None of it is free, and none of it is restructuring for its own sake. Each piece earns its place by arriving after something specific went wrong. Adopting all of it pre-emptively, on a system that has not yet hurt you, is its own kind of waste.

What it buys

  • Restructuring that is provably behaviour-preserving, byte for byte
  • A rename or a stale copy fails CI instead of quietly changing someone's numbers
  • Substantial changes delegated inside a module and verified at its boundary
  • Documentation that cannot drift from the code without failing a test
  • Capabilities you had written off — once a boundary is testable, “we can't do that” stops being a belief and becomes a claim you can check
The trade, stated plainly

You spend time now, deterministically, to avoid spending an unknown amount later, under pressure, with someone waiting. That is the whole bargain — and it is a good one precisely because the second kind of time is so much more expensive than the first.
